# PART 1. 제품 이해하기

## 1.1 한 줄 요약

녹내장 환자가 **집에서 잰 안압과 점안 기록**을 스마트 기기로 자동 수집해, 담당 의료진이 진료실 밖의 상태까지 보고 판단하게 하는 시스템입니다.

## 1.2 왜 필요한가 (임상 배경)

개발하다 보면 판단이 필요한 순간이 옵니다. 왜 이렇게 만들었는지 알고 계시면 좋습니다.

**녹내장은 안압 관리가 전부입니다.** 손상된 시신경은 되돌릴 수 없어서, 안압을 목표치 아래로 유지해 진행을 늦추는 것이 유일한 치료입니다.

여기에 두 가지 문제가 있습니다.

**첫째, 진료실 안압은 하루 중 한 점입니다.** 안압은 하루 사이에도 오르내리고 특히 **기상 직후가 가장 높습니다.** 낮에 병원에서 잰 값이 정상이어도 새벽에 높았다면 시신경은 계속 손상됩니다. 그래서 가정 측정과 **일중 변동폭**을 봅니다.

**둘째, 점안약을 거릅니다.** 녹내장 약은 증상이 없어도 평생 넣어야 해서 순응도가 낮습니다. 넣지 않으면 안압이 오르는데, 환자는 "잘 넣고 있다"고 말하는 경우가 많습니다. 그래서 **기기로 자동 기록**하고, 거른 날과 안압을 나란히 봅니다.

이 앱의 거의 모든 기능이 이 두 문제에서 나왔습니다.

## 2.2 환자 앱 둘러보기 (15분)

상단 토글에서 **환자 앱**을 선택하세요.

**① 로그인 화면**
아무 값이나 넣고 로그인하거나, SNS 버튼(카카오·구글·위챗 등) 또는 비회원으로 들어갑니다. 회원가입 탭에는 기기 시리얼 등록과 대여/개인소유 선택이 있습니다.

**② 홈 탭**
좌·우안 게이지, 알림 카드, 오늘 점안 진행률, 최근 7일 추세가 보입니다. **우상단 종 아이콘**을 눌러 알림 패널을 확인하세요.

**③ 안압 탭 — 여기가 핵심입니다**
`측정` 버튼을 누르면 패널이 열리고, **아무 버튼도 누르지 않았는데** 몇 초 뒤 우안 값이 들어오고 이어서 좌안이 채워집니다. 이것이 기기 신호 시뮬레이션입니다. 값을 눌러 수정하거나, 자동측정 토글을 끄면 직접 입력할 수 있습니다.

아래 `기간 분석`으로 바꾸면 그래프 3종(Chart·Scatter·Diurnal)과 점안↔안압 병렬 차트, 일중 변동폭이 나옵니다.

**④ 점안 탭**
기기 연결 현황(기기1·기기2), 순응도 강화 카드, 약 목록이 있습니다. **몇 초 기다리면** 자동 연결된 약의 좌·우가 저절로 체크됩니다. 약을 누르면 상세로 들어가 약병 관리·부작용 기록·기기 변경을 볼 수 있습니다. `약 추가`에서 e약은요 검색과 대우제약 제품 목록을 확인하세요.

`순응도 분석` 탭에는 약제별·시각별·요일별 순응도와 **놓치는 이유 찾기**가 있습니다.

**⑤ 문진 · 건강 탭**
생활습관 12항목 문진과 워치 연동 데이터입니다.

## 3.4 코드를 읽는 요령

**순수 함수부터 보세요.** `deviceState`, `rentAlert`, `adhLevel`, `bottleState`, `overallAdherence`, `rootCauses`는 화면과 무관한 판정 로직입니다. 이 여섯 개를 이해하면 앱의 90%를 이해한 것입니다.

**데이터 흐름은 단방향입니다.** `PatientApp`과 `ClinicianWeb`이 상태를 들고, 화면 컴포넌트는 props로 받아 표시하고 콜백으로 올립니다. Redux 같은 것은 없습니다.

**주석에 `실제 구현에서는` 이 있으면** 그 자리가 교체 지점입니다.

# PART 4. 도메인 규칙 명세

여기 있는 판정식은 **서버에도 동일하게 구현**해야 합니다. 프런트와 서버 결과가 다르면 안 됩니다.

## 4.1 안압 판정

```
게이지 색상:
  값 ≤ 목표          → 초록 (목표 이내)
  목표 < 값 ≤ 목표+3  → 주황 (근접)
  값 > 목표+3        → 빨강 (초과)

일중 변동폭 = 그날 최고 − 최저
  < 2      → 안정
  2 ~ 5    → 관찰
  ≥ 5      → 주의
```

좌·우안은 **각각 독립된 레코드**입니다. 한쪽만 측정한 경우가 정상 케이스이므로 한 행에 od/os를 묶지 마세요.

## 4.2 순응도

```
순응도 = 실제 점안 횟수 / 예정 점안 횟수 × 100

단위: 약제 × 예정 시각 × 눈(좌/우) 1건
  예) 1일 2회 양안 → 하루 4건

목표: 80% 이상
```

**분모가 핵심입니다.** 처방이 등록되면 매일 자정에 다음 날 `dose_event` 행을 `taken=false`로 미리 만들어야 "거른 것"과 "기록 없음"이 구분됩니다. 여기가 틀리면 모든 통계와 알림이 어긋납니다.

집계 축은 여섯 가지입니다 — 전체 / 일별 / 약제별 / 시각별 / 좌우안별 / 요일별.

## 4.3 약병 수명

```
다회용: 개봉일 + 28일 = 폐기 예정일
  D-3 이하 → 교체 임박 알림
  경과     → 폐기 필요 (오염 위험)

일회용: 남은 개수 ≤ 5 → 리필 알림
```

## 4.4 기기 반납 알림 (5단계)

`dd = 반납예정일 − 오늘`

| dd | 단계 | 기본 채널 | 데이터 수신 |
|---|---|---|---|
| 3 ~ 2 | 안내 | 푸시 | 정상 |
| 1 | 알림 | 푸시 + SMS | 정상 |
| 0 | 당일 | 푸시 + SMS | 정상 |
| −1 ~ −2 | 연체 | 푸시 + SMS + 콜 | 정상 |
| ≤ −3 | **수신 중단** | 푸시 + SMS + 콜 | **차단** |

유예 기간(기본 3일)은 기관별로 0~14일 설정 가능합니다.

**수신 중단 정책이 중요합니다.** 서버는 업로드를 거부하되, **앱은 로컬 저장을 계속 유지**합니다. 행정적 사유로 환자 데이터를 버리게 만들면 안 됩니다. 반납·연장 시 보관분을 일괄 재전송합니다.

개인 소유 기기는 반납 개념이 없으므로 이 판정에서 제외합니다.

## 4.5 순응도 알림 강화 (4단계)

최근 14일 순응도와 연속 누락으로 판정합니다.

| 단계 | 조건 | 사전 알림 | 재알림 | 보호자 | 의료진 |
|---|---|---|---|---|---|
| 양호 | 90% 이상 | — | — | — | — |
| 주의 | 90% 미만 | 30분 전 | — | — | — |
| 경고 | 80% 미만 | 30분 전 | 15분 × 1회 | — | — |
| 위험 | 70% 미만 또는 연속 3일 | 45분 전 | 15분 × 2회 | ○ | ○ |

특정 시각의 순응도가 85% 미만이면 **그 시각만** 15분 더 일찍 알립니다. 보호자 알림은 **환자 동의**가 있어야 발송합니다.

## 4.6 원인 분석

각 후보의 **영향도(%p)**는 전체 평균 대비 하락폭입니다.

| 분류 | 판정 |
|---|---|
| 부작용 | 보고일 기준 이전 14일 vs 이후 순응도 차이 (표본 8건 이상) |
| 투약 시각 | 최저 시각과 전체 평균 차이 ≥ 3%p |
| 요일 | 최저 요일과 전체 평균 차이 ≥ 3%p |
| 좌·우안 | 양쪽 차이 ≥ 3%p |
| 약제 | 최저 약제와 최고 약제 차이 ≥ 5%p |
| 약병 | 폐기 임박·소진 상태 존재 |

**인과 판정이 아니라 연관성 제시**입니다. 화면 문구도 그렇게 되어 있으니 바꾸지 마세요(SaMD 경계).

## 5.2 파일 분리 구조

```
src/
├─ theme/        tokens.js · atoms.jsx
├─ domain/       iop.js · adherence.js · notify.js · bottle.js   ← 순수 함수, 테스트 대상
├─ api/          client.js · patients.js · devices.js · doses.js …
├─ ble/          tonometer.js · dropSensor.js · queue.js
├─ charts/       IopGraph · AdhIopChart · FlucChart
├─ patient/      화면 + components/
└─ clinician/    화면 + modals/
```

**분리 순서**는 `theme` → `domain` → `charts` → `atoms` → 화면입니다. `domain`을 먼저 빼면 단위 테스트를 바로 붙일 수 있습니다.

**첫 작업으로 이것을 권합니다.** 파일 이동과 import 정리만으로 끝나면서 테스트 기반이 생기고, 백엔드 없이도 프런트가 병렬 진행됩니다.

## 5.3 상태 관리

| 종류 | 도구 | 예 |
|---|---|---|
| 서버 데이터 | **TanStack Query** | 환자 목록, 측정 이력, 순응도 |
| 세션·권한 | Context | 로그인 사용자, 역할 |
| 화면 로컬 | `useState` | 모달, 필터, 정렬 |

프로토타입의 정렬·필터는 클라이언트에서 하지만, 실서비스에서는 **서버 파라미터로 넘기세요.** 환자가 수천 명이면 클라이언트 정렬은 성립하지 않습니다.

## 5.5 BLE 연동

### 시뮬레이션 교체 위치

```js
// 안압 — MeasurePanel 내부 useEffect (L1979 부근)
timers.current.push(setTimeout(() => { /* 값 생성 */ }, 1900 + i * 2100));

// 점안 — DropsScreen 내부 useEffect (L3128 부근)
timers.push(setTimeout(() => { /* 체크 처리 */ }, 5200 + idx * 3400));

// 페어링 스캔 — BtPairModal 내부 useEffect (L1207)
setTimeout(() => setFound(devices), ...)   // → navigator.bluetooth.requestDevice()
```

### 권장 GATT 구조

```
Service: 안압 측정
├─ measurement   [notify]  { seq, eye(0=OD/1=OS), value_x10, quality, epoch }
├─ battery       [read, notify]
└─ device_info   [read]    serial, firmware

Service: 점안 감지
├─ dose_event    [notify]  { seq, eye, epoch }
└─ bottle_state  [read]    남은 방울 추정
```

`seq`는 기기가 증가시키는 시퀀스로, 서버 멱등키(`measurement_uid`)의 원천입니다.

### 플랫폼 선택

| 방식 | 장점 | 제약 |
|---|---|---|
| Web Bluetooth (PWA) | 배포 간편 | **iOS Safari 미지원** |
| **Capacitor + 네이티브 BLE** | 기존 코드 재사용, iOS 지원 | 앱스토어 심사 |
| React Native | 백그라운드 유리 | UI 전면 재작성 |

**Capacitor를 권합니다.** 현재 React 코드를 거의 그대로 옮기면서 iOS·안드로이드 BLE와 푸시를 모두 확보할 수 있습니다.

### 오프라인 큐

1. BLE 수신 → **로컬(IndexedDB)에 먼저 기록**
2. 온라인 감지 시 배치 업로드
3. 서버가 `uid`로 중복 제거
4. 성공분만 큐에서 제거

**`RENTAL_OVERDUE`로 거부되어도 큐를 비우지 마세요.** 반납·연장 후 재전송해야 합니다.

## 5.6 푸시 알림

`usePush`(L1650)는 브라우저 Notification API입니다. 실제로는 FCM/APNs 토큰을 서버에 등록하고 배치가 발송합니다.

- 페이로드에 **진단명·측정값 금지** — 잠금화면에 노출됩니다
- 알림 클릭 시 딥링크(점안 → 점안 탭, 반납 → 설정)
- `NotRegistered` 응답 시 토큰 즉시 폐기

## 5.7 API 클라이언트 골자

```js
async function request(path, opts = {}) {
  const res = await fetch(BASE + path, {
    ...opts,
    headers: { "Content-Type": "application/json", Authorization: `Bearer ${token()}`, ...opts.headers },
  });
  if (res.status === 401) { await refresh(); return request(path, opts); }
  const json = await res.json();
  if (!res.ok) throw new ApiError(json.error);
  return json.data;
}
```

오류는 `error.code`로 분기합니다. `RENTAL_OVERDUE`는 실패가 아니라 **큐 유지 신호**입니다.

## 부록. 자주 나올 질문

**Q. 왜 좌·우를 한 행에 안 넣나요?**
한쪽만 측정하는 경우가 정상 케이스입니다. 묶으면 NULL 처리가 지저분해지고 순응도 분모 계산도 꼬입니다.

**Q. 순응도를 서버에서 계산할까요, 클라이언트에서 할까요?**
90일·환자 1명 기준 수백 행이라 클라이언트로 충분합니다. 다만 의료진 웹의 환자 목록처럼 **여러 환자를 한 번에** 보는 화면은 서버 집계값을 내려받으세요.

**Q. 데모 데이터의 날짜가 2026년인데요?**
`TODAY_REF`(L101)로 기준일을 고정해 시나리오를 재현합니다. 실서비스 전환 시 해제합니다.

**Q. 화면 문구를 바꿔도 되나요?**
UI 문구는 자유롭게 다듬으셔도 됩니다. 단 **"인과 판정이 아니라 연관성 제시"**, **"진단·치료를 대체하지 않음"** 같은 고지는 SaMD 규제 관련이라 유지해야 합니다.

**Q. 어디부터 손대야 하나요?**
`domain/` 폴더 분리입니다. PART 5.2를 보세요.
