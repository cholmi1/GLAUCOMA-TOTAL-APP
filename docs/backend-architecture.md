# 안압케어 백엔드 아키텍처 설계

C&V Tech · GLAUCOMA TOTAL APP / v1.0 / 2026-08

현재 프런트엔드 프로토타입이 클라이언트 상태로 다루고 있는 데이터를 서버로 옮기기 위한 설계 문서입니다. 함께 보는 문서: [`db-schema.md`](db-schema.md), [`api-spec.md`](api-spec.md), [`notify-integration-spec.md`](notify-integration-spec.md)

---

## 1. 시스템 구성

```
[환자 앱]  iOS / Android / PWA
     │  HTTPS + JWT
     ▼
┌─────────────────────────────────────────────┐
│  API 게이트웨이 (인증 · 레이트리밋 · 로깅)      │
└─────────────────────────────────────────────┘
     │
     ├─▶ [Core API]      환자·측정·점안·문진·기기
     ├─▶ [Analytics API] 순응도 집계 · 원인 분석
     ├─▶ [Notify Worker] 배치 스케줄러 · 발송 큐
     └─▶ [Ingest API]    CVT200 측정 업로드 (대량·오프라인 동기화)
     │
     ▼
[PostgreSQL]  주 저장소 (기관별 논리 분리)
[Redis]       세션 · 큐 · 집계 캐시
[Object Storage] 보고서 PDF · 내보내기 파일
     ▲
     │  HTTPS + JWT
[의료진 웹]  React SPA
```

**분리 원칙** — Ingest API를 Core에서 떼어 놓습니다. 가정용 기기가 네트워크가 회복될 때 며칠치를 한꺼번에 올리는 패턴이 있어, 진료 중인 의료진 웹의 응답 속도에 영향을 주지 않아야 합니다.

## 2. 테넌시 모델

기관(organization)을 최상위 경계로 두는 **단일 DB · 논리 분리** 방식입니다.

- 환자·기기·측정·처방 등 거의 모든 테이블에 `org_id`를 두고, 애플리케이션 계층에서 세션의 `org_id`를 강제로 주입합니다.
- PostgreSQL **Row Level Security**를 함께 걸어 애플리케이션 버그가 있어도 다른 기관 데이터가 새지 않도록 이중 방어합니다.
- 기관 수가 수백 단위를 넘어가면 국가별 물리 분리로 전환합니다(아래 5절).

환자 한 명이 두 기관에 다니는 경우가 있으므로, 환자 계정(`patient_account`)과 기관별 진료 등록(`patient`)을 분리했습니다. 계정은 전역, 진료 기록은 기관 소속입니다.

## 3. 인증 · 인가

### 3.1 환자

| 경로 | 방식 |
|---|---|
| 개별 가입 | 로그인 ID + 비밀번호(Argon2id 해시) |
| SNS | OAuth 2.0 / OIDC — 카카오·네이버 / Google·Apple·Facebook / WeChat·Weibo·QQ |
| 비회원 | 기기 고유 ID 기반 임시 토큰, 서버 저장 없음 |

- SNS 계정은 `oauth_identity` 테이블에 `(provider, provider_uid)`로 연결합니다. 한 계정에 여러 provider를 붙일 수 있습니다.
- **비회원은 서버에 데이터를 남기지 않습니다.** 앱 로컬에만 저장하고, 나중에 가입하면 로컬 기록을 일괄 업로드해 계정으로 이관합니다(`POST /me/migrate`).
- 토큰은 액세스 15분 / 리프레시 30일. 리프레시 토큰은 회전(rotation)시키고 재사용이 감지되면 전체 세션을 무효화합니다.

### 3.2 직원

기관 관리자가 계정을 생성하며, **자가 가입 경로가 없습니다.** 역할은 `admin` / `physician` / `trainer` 셋이고 권한은 서버에서 판정합니다.

| 기능 | admin | physician | trainer |
|---|:---:|:---:|:---:|
| 직원 계정 관리 | O | – | – |
| 알림 스케줄·채널·강화 기준 설정 | O | – | – |
| 목표 안압 변경 · 처방 등록 | O | O | – |
| 측정 결과 제외 처리 | O | O | – |
| 환자 등록 · 기기 배정 · 반납 처리 | O | O | O |
| 기관 데이터 내보내기 | O | – | – |

프런트엔드의 버튼 노출은 UX일 뿐이며, **모든 판정은 서버 미들웨어에서 다시 합니다.**

## 4. 측정 데이터 수집

### 4.1 업로드 경로

CVT200 → 환자 앱(BLE) → `POST /ingest/measurements`

기기가 직접 인터넷에 붙지 않고 앱을 경유합니다. 기기 인증은 시리얼 번호 + 기기 발급 키로 하며, 앱은 자신이 연동한 기기의 데이터만 올릴 수 있습니다.

### 4.2 멱등성

오프라인 재전송 때문에 같은 측정이 여러 번 올라옵니다. 기기가 생성한 `measurement_uid`(기기 시리얼 + 기기 내부 시퀀스)를 유니크 키로 두어 중복을 서버에서 흡수합니다. 클라이언트는 실패 시 그냥 다시 보내면 됩니다.

### 4.3 수신 중단 정책

대여 기기의 반납 연체가 유예 기간(기본 3일)을 넘으면 해당 기기의 업로드를 **거부**합니다.

- 응답: `202 Accepted` + `{ "stored": false, "reason": "RENTAL_OVERDUE", "resume_hint": "..." }`
- 앱은 로컬에 계속 보관합니다. **데이터를 버리게 만들면 안 됩니다.**
- 반납 또는 기간 연장이 처리되면 앱이 보관분을 일괄 재전송하고 서버가 정상 수용합니다.

## 5. 국가별 데이터 처리

| 지역 | 규제 | 대응 |
|---|---|---|
| 한국 | 개인정보보호법 · 의료법 | 국내 리전 저장, 진료기록 보존 의무 확인 |
| 미국 | HIPAA | BAA 체결 가능한 클라우드, 접근 로그 보존 |
| 중국 | PIPL | 국경 간 이전 제한 → **중국 리전 별도 배포** |
| EU | GDPR | 삭제권·이동권 API 제공 |

중국은 데이터의 국외 반출이 제한되므로 처음부터 별도 배포를 전제로 설계합니다. 코드베이스는 공유하되 DB와 발송 채널(WeChat·SMS 사업자)을 리전별로 분리합니다.

## 6. 보안

- **비밀번호**: Argon2id. 평문·복호화 가능 암호화 모두 금지. 의료진 웹의 환자 비밀번호 표시는 재설정 링크 발송으로만 제공합니다.
- **전송**: TLS 1.2 이상. 인증서 피닝은 모바일 앱에 적용.
- **저장 시 암호화**: 연락처·이메일·생년월일 등 식별정보 컬럼은 애플리케이션 레벨 암호화(AES-256-GCM, KMS 관리 키). 검색이 필요한 필드는 블라인드 인덱스(HMAC) 병행.
- **감사 로그**: 조회를 포함한 모든 환자 데이터 접근을 기록합니다. 의료 데이터는 "누가 언제 봤는지"가 규제 요구사항입니다.
- **불변 로그**: 알림 발송 로그와 감사 로그는 UPDATE·DELETE를 권한에서 제거하고 정정은 반대 기록 추가로 처리합니다.
- **레이트리밋**: 로그인 IP당 10회/분, 계정당 5회/분. Ingest는 기기당 60회/분.

## 7. 순응도 집계 전략

순응도는 `dose_event` 테이블(점안 1회 = 1행)에서 계산합니다. 프런트엔드가 이미 이 구조로 동작하므로 서버도 동일하게 맞춥니다.

**예약 행 방식** — 처방이 등록되면 스케줄러가 매일 자정에 다음 날의 `dose_event` 행을 `taken=false`로 미리 생성합니다. 환자가 체크하면 `taken=true`, `taken_at`이 채워집니다. 이렇게 하면 "거른 것"과 "기록이 없는 것"이 구분되고, 분모가 명확해집니다.

**집계 캐시** — 일별 순응도는 `adherence_daily` 요약 테이블에 야간 배치로 적재합니다. 기간 조회는 요약 테이블을 읽고, 당일분만 원본에서 실시간 계산해 합칩니다.

**원인 분석**은 온디맨드로 계산합니다. 환자 1명 · 90일 기준 수백 행 수준이라 사전 계산이 불필요합니다.

## 8. 배치 작업

| 작업 | 주기 | 내용 |
|---|---|---|
| 다음 날 dose_event 생성 | 매일 00:05 | 활성 처방 기준 |
| 순응도 일별 집계 | 매일 01:00 | `adherence_daily` 적재 |
| 반납 알림 판정·발송 | 기관별 설정 시각 | D-3 / D-1 / 당일 / 연체 |
| 순응도 강화 단계 재판정 | 매일 02:00 | 최근 14일 기준, 변경 시 앱 알림 정책 갱신 |
| 약병 폐기·소진 알림 | 매일 08:00 | 개봉 후 28일, 잔량 임계 |
| 감사 로그 아카이빙 | 매월 | 3년 경과분 콜드 스토리지 이동 |

배치는 기관 타임존 기준으로 개별 실행하며, 실행 결과를 `job_run` 테이블에 남깁니다.

## 9. 개발 순서 제안

1. **인증 · 기관 · 직원 · 환자** — 로그인과 고객 DB만으로 의료진 웹의 뼈대가 섭니다
2. **기기 · 측정 수집** — Ingest API와 멱등성, 대여/반납 상태
3. **처방 · dose_event · 순응도 집계** — 점안 관리의 핵심
4. **알림 배치 · 감사 로그** — 반납 알림부터, 푸시 채널 연동
5. **문진 · 워치 연동 · 원인 분석** — 부가 가치 영역

1~3단계까지가 실제 임상 사용의 최소 단위입니다. 4단계는 발신번호 등록·발송사 계약에 시간이 걸리므로 1단계부터 병행 준비하시기를 권합니다.
